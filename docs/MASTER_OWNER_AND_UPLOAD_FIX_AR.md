# المالك الرئيسي Master Owner + إصلاح «فشل الرفع»

> تقرير تنفيذي: السبب الحقيقي، ما تغيّر في الكود وقاعدة البيانات، وكيف تتحقق بنفسك على الإنتاج.

---

## 1) الملخص التنفيذي

| البند | قبل | بعد |
|---|---|---|
| صلاحية المالك الرئيسي على أي متجر | كانت موجودة في API/RLS لكن **لوحة المتجر نفسها** (`rshaf.waathba.com/admin`) كانت ترفضه لأنه ليس `store_member` | يدخل أي متجر بنفس واجهة صاحب المتجر وكل وظائفها |
| تغيير النطاق الفرعي | متاح من صفحة «النطاقات» فقط | متاح أيضًا من داخل المتجر — يعمل لأي حالة (منها المسلّم) |
| رسالة «فشل الرفع» | رسالة عامة تُخفي الخطأ الحقيقي (استجابة 500 فارغة) | رسالة عربية واضحة + رمز الخطأ + التفصيل التقني |
| سبب فشل الرفع | خطأ في طبقة التخزين غير ظاهر + اعتماد الرفع على `SUPABASE_SECRET_KEY` | الرفع يجري **بجلسة المستخدم** عبر RLS (لا يحتاج المفتاح السري)، والخطأ يُعرض بوضوح |
| فحص التخزين | لا يوجد | بطاقة **«فحص رفع الصور»** داخل كل متجر تفحص الطبقات الأربع فعليًا |
| تسجيل النشاط | كان يعتمد على المفتاح السري، وفشله يُظهر «فشل الحفظ» مع أن البيانات حُفظت | يعمل بجلسة المستخدم، وفشله لا يُسقط العملية الأصلية |
| حفظ الإعدادات/المظهر/الآيبان | **يفشل دائمًا في الإنتاج** (`PGRST204`: أعمدة ناقصة في `store_settings`) | الترحيل 0004 يضيف الأعمدة — ويعمل مع المالك وصاحب المتجر |
| دخول المالك إلى `rshaf.waathba.com/admin` | كوكي الجلسة تُكتب للمضيف الذي سجّل الدخول فقط → يظهر كغير مسجَّل على النطاق الفرعي | كوكي الجلسة على النطاق الأب `.waathba.com` → الدخول مرة واحدة يعمل على كل النطاقات الفرعية |

## 2) السبب الحقيقي لرسالة «فشل الرفع»

### 2.1 مسار الرفع الفعلي (الواجهة → API → التخزين → قاعدة البيانات)

```
components/admin/upload-field.tsx
        │  POST /api/upload  (multipart: storeId, folder, file)
        ▼
app/api/upload/route.ts
        │  requireStoreActor(storeId)  →  lib/api.ts  →  lib/authorize.ts
        │        canManageStore(actor, storeId):  role === "owner" ? true : عضويته فقط
        ▼
lib/services/supabase.ts → uploadImage()
        │  (سابقًا) supabaseAdmin()  ← مفتاح SUPABASE_SECRET_KEY
        ▼
Supabase Storage: bucket «store-assets» → stores/{store_id}/{folder}/{file}
        ▼
activity_logs (تسجيل النشاط)
```

### 2.2 لماذا كانت الرسالة عامة؟

في `components/admin/upload-field.tsx` كان السطر:

```ts
const data = await res.json().catch(() => ({}));
if (!res.ok) throw new Error(data.error ?? "فشل الرفع");
```

أي أن **«فشل الرفع» = بديل احتياطي** يظهر فقط عندما لا يعود الخادم بجسم JSON يحوي `error`.
وبما أن **كل** أخطاء الصلاحيات والتحقق في المنصة تُعاد كـ JSON
(`{"error":"لا تملك صلاحية الوصول إلى بيانات متجر آخر"}` … إلخ)، فإن ظهور «فشل الرفع»
يعني حرفيًا: **لا علاقة للأمر بالصلاحيات** — الخطأ وقع بعد اجتياز فحص الصلاحية،
وخرج من الخادم كاستجابة **500 بلا جسم** لأن `POST /api/upload` لم يكن محاطًا بـ `try/catch`.

### 2.3 الدليل العملي (إعادة إنتاج حقيقية)

شغّلنا الكود الأصلي (commit `297e3ab`) أمام خادم Supabase وهمي يقلّد السلوك الفعلي
(`scripts/stub-supabase.mjs` + `scripts/repro-upload.mjs`)، وطلبنا رفع شعار بحساب
**المالك الرئيسي**:

| الحالة | الكود الأصلي | بعد الإصلاح |
|---|---|---|
| مفتاح الخادم السري غير مضبوط | فشل الدخول أصلًا (500) → **يعني: المفتاح موجود في الإنتاج** لأنه يدخل اللوحة | ✅ الرفع ينحج (201) |
| المفتاح مضبوط لكنه خاطئ | `HTTP 500` + **جسم فارغ** → «فشل الرفع» | ✅ الرفع ينجح (201) |
| خزنة `store-assets` غير موجودة | `HTTP 500` + **جسم فارغ** → «فشل الرفع» | ⚠️ `500` برسالة صريحة: «خزنة الصور غير موجودة… نفّذ الترحيل 0003» |
| كل شيء سليم | 201 ✔ | 201 ✔ |

> في نفس التجربة، نجح **صاحب المتجر** في الرفع لمتجره وفشل لمتجر آخر (403) —
> أي أن الفشل في الحالات أعلاه كان يُصيب المالك وصاحب المتجر **بالساوي**:
> دليل قاطع على أنه ليس قيدًا على المالك الرئيسي.

### 2.4 الاستنتاج

* السبب المباشر: **استثناء غير ملتقط في طبقة التخزين** (خزنة غير موجودة، أو مفتاح سري خاطئ،
  أو رفض RLS للتخزين) كان يخرج كـ `500` بلا جسم، فتظهر «فشل الرفع».
* السبب الجذري الهندسي: **اعتماد رفع الصور على `SUPABASE_SECRET_KEY`** في الخادم رغم أن
  الصلاحية الحقيقية يجب أن تُحسم بـ RLS بجلسة المستخدم — وهذا ما جعل أي خلل في المفتاح
  أو الخزنة يُعطّل الرفع بالكامل، ورسالة الخطأ لا تقول شيئًا.
* لذلك أصلحنا الاثنين: **السبب** (الرفع بجلسة المستخدم + إصلاح/إنشاء الخزنة + سياسات RLS)
  و**الشفافية** (رسائل JSON واضحة + بطاقة فحص).

### 2.5 سبب ثانٍ مؤكد: فشل **حفظ الإعدادات** في الإنتاج (PGRST204)

هذا سبب مستقل تمامًا عن الرفع، وكشفتْه مقارنة مخطط قاعدة البيانات مع ما يكتبه التطبيق فعلًا:

* طبقة الخدمة (`lib/services/supabase.ts` → `updateStoreSettings`) ترسل **دائمًا** هذه الأعمدة:
  `footer_bg_color`, `iban_rajhi`, `iban_alinmaa`, `iban_alahli`.
* هذه الأعمدة كانت موجودة في مخطط الوضع التجريبي (`lib/local/db.ts`) و**غائبة** عن مخطط
  الإنتاج (`supabase/migrations/0001_init.sql`) — فرقٌ صامت بين البيئتين.
* النتيجة في الإنتاج: PostgREST يرد
  `PGRST204 — Could not find the 'footer_bg_color' column of 'store_settings' in the schema cache`
  فيفشل **أي** حفظ للإعدادات أو المظهر أو الآيبانات من لوحة المالك ومن لوحة صاحب المتجر معًا.
* الإصلاح: الترحيل `0004_store_settings_columns.sql` (إضافة أعمدة فقط، آمن للتكرار)، وأُضيفت
  الأعمدة إلى `0001_init.sql` كذلك كي لا يتكرر الفرق في أي تركيب جديد.

### 2.6 سبب ثالث: المالك لا يستطيع استخدام لوحة المتجر على نطاق المتجر

* لوحة المتجر (`rshaf.waathba.com/admin`) كانت تسمح لصاحب المتجر فقط
  (`user.memberships.some(...)`) → المالك الرئيسي يُحوَّل إلى تسجيل الدخول.
* وحتى بعد السماح له بها، كوكي جلسة Supabase تُكتب افتراضيًا للمضيف الذي سجّل الدخول
  (`waathba.com`) فقط، فلا تُرسَل إلى `rshaf.waathba.com` → يظهر المالك كأنه غير مسجَّل.
* الإصلاح: (١) `app/admin/(client)/layout.tsx` و`app/admin/page.tsx` يسمحان للمالك الرئيسي
  عبر `canAccessStorePanel` (نفس الواجهة والوظائف لصاحب المتجر)، (٢) كتابة كوكي الجلسة على
  النطاق الأب `.waathba.com` (`sharedCookieDomain` في `lib/constants.ts`، مطبَّقة على عميل
  Supabase وعلى جلسة الوضع التجريبي وعلى تسجيل الخروج).

## 3) ما تغيّر

### 3.1 قاعدة البيانات — `supabase/migrations/0003_...` و `0004_...`

* دوال صلاحيات موحّدة: `is_master_owner()` و`is_platform_owner()` (توافق) و`is_store_member()` و`can_manage_store()`.
* إعادة كتابة **كل** سياسات الجداول المتعلقة بالمتاجر بحيث:
  * المالك الرئيسي: قراءة/كتابة/حذف في **كل** متجر وفي **كل** حالة (preparing/delivered/…).
  * صاحب المتجر: متجره فقط.
* `protect_store_fields` تُقيّد **عضو المتجر** فقط (النطاق، الحالة، بيانات العميل، بيانات التسليم)
  ولا تمسّ المالك الرئيسي → تغيير النطاق الفرعي بعد التسليم يعمل.
* **التخزين**: `store-assets` تُنشأ/تُصلَح تلقائيًا (عامة، 5MB، أنواع الصور)،
  مع سياسات كتابة:
  * `store_assets_master_*` → المالك الرئيسي في أي مسار (بما فيها أصول الموقع `stores/site/…`).
  * `store_assets_member_*` → صاحب المتجر **فقط** داخل `stores/<معرّف متجره>/…`.
* `activity_logs`: الكتابة بجلسة المستخدم (لا مفتاح سري)، والقراءة للمالك أو لأعضاء المتجر.
* الملف آمن للتكرار (idempotent) — لا يحذف أي بيانات، DDL + تهيئة الخزنة فقط.
* `0004_store_settings_columns.sql`: يضيف أعمدة `store_settings` الناقصة
  (`footer_bg_color`, `iban_rajhi`, `iban_alinmaa`, `iban_alahli`) + `notify pgrst, 'reload schema'`.
  بدونه يفشل حفظ الإعدادات والمظهر في الإنتاج (`PGRST204`).

### 3.2 طبقة الخدمة — `lib/services/supabase.ts` و `lib/services/local.ts`

* `uploadImage()`: الرفع **بجلسة المستخدم** (RLS). احتياط واحد فقط: إن رفضت RLS الكتابة
  (قاعدة بيانات لم يُنفَّذ عليها 0003 بعد) وكان المفتاح السري متاحًا، تُعاد المحاولة به.
* `deleteImage()` جديدة: حذف فعلي للصور المستبدلة (Supabase Storage أو `.data/uploads`).
* `storageHealth()` جديدة: فحص الخزنة + رفع/حذف اختباري حقيقي بحساب الجلسة.
* `logActivity()`: بجلسة المستخدم، و**لا يُسقط العملية الأصلية** عند فشله.
* أخطاء التخزين تُحوَّل إلى `StorageError` برموز مفهومة
  (`bucket_missing`, `permission_denied`, `server_key_missing`, `too_large`, `mime_not_allowed`, `network`, `unexpected`).

### 3.3 طبقة API

* `POST /api/upload`: كل خطأ → JSON برسالة عربية + `code` + `detail` (لا استجابة فارغة بعد اليوم).
  وتحسين قبول الأنواع: إن أرسل المتصفح نوعًا فارغًا، نستنتجه من الامتداد.
* `DELETE /api/upload`: حذف صورة (استبدال/تنظيف) بفحص صلاحية على المتجر.
* `GET /api/upload/health?storeId=…`: فحص طبقة التخزين (المالك الرئيسي فقط).
* 15 مسارًا للكتابة (متاجر/منتجات/أقسام/صفحات/SEO/تصميم/إعدادات/حالة/تسليم/نشاط…)
  أصبحت تُرجع **JSON واضحًا** في أي خطأ غير متوقع بدل استجابة فارغة.

### 3.4 الواجهة

* **المالك الرئيسي يدخل لوحة أي متجر** بنفس واجهة صاحب المتجر:
  `app/admin/(client)/layout.tsx` و`app/admin/page.tsx` صارا يسمحان له
  (`canAccessStorePanel`) بدل اشتراط العضوية، مع شارة «تدخل كمالك رئيسي» وروابط بين اللوحتين.
* زر **«لوحة المتجر»** + **تغيير النطاق الفرعي من داخل المتجر** في صفحة إدارة المتجر.
* بطاقة **«فحص رفع الصور»** في صفحة كل متجر (تفحص: الخزنة، عموميتها، الرفع بالجلسة، الحذف، المفتاح السري).
* حقل الرفع: قراءة آمنة للردود، عرض رمز HTTP ورسالة الخادم الحقيقية، وحذف الصورة من التخزين عند إزالتها.

### 3.5 مصفوفة الصلاحيات بعد التعديل

| العملية | المالك الرئيسي | صاحب المتجر | الزائر |
|---|---|---|---|
| عرض/تعديل بيانات أي متجر (اسم، وصف، تواصل، شعار، غلاف) | ✅ أي متجر | ✅ متجره فقط | ❌ (قراءة المتجر المسلّم فقط) |
| تغيير النطاق الفرعي (حتى بعد التسليم) | ✅ | ❌ | ❌ |
| تغيير الحالة/التسليم/الإنشاء/الحذف | ✅ | ❌ | ❌ |
| منتجات/أقسام/صفحات/صور/ترتيب/SEO/تصميم/إعدادات | ✅ أي متجر | ✅ متجره فقط | ❌ |

> ملاحظة محتوى (اختيارية): نصوص الموقع العامة في لوحة المالك ما زالت تذكر
> `name.wathbastore.com` بينما النطاق الرسمي الآن `waathba.com` — تُعدّل من
> **لوحة المالك → إعدادات الموقع**.

## 4) خطوات التشغيل على الإنتاج

1. **نفّذ الترحيلين** في Supabase → SQL Editor بالترتيب:
   ```
   supabase/migrations/0003_master_owner_permissions.sql   ← صلاحيات المالك + سياسات التخزين + إنشاء/إصلاح الخزنة
   supabase/migrations/0004_store_settings_columns.sql     ← أعمدة الإعدادات الناقصة (PGRST204)
   ```
   كلاهما آمن للتكرار ولا يحذف أي بيانات.
2. تأكد من متغيرات البيئة على Cloudflare:
   * `NEXT_PUBLIC_SUPABASE_URL` — رابط المشروع فقط (بلا `/rest/v1`).
   * `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
   * `SUPABASE_SECRET_KEY` — **لم يعد مطلوبًا لرفع الصور**، لكنه مطلوب لتسليم المتاجر (إنشاء حساب العميل).
3. انشر النسخة الجديدة (`npm run cf-deploy`، أو نشر تلقائي بعد دمج الفرع).
4. افتح: لوحة المالك → أي متجر → **«فحص رفع الصور»** → «تشغيل الفحص».
   يجب أن تظهر كل البنود «سليم». إن ظهر بند مشكلة فستجد تحته خطوة الإصلاح بالضبط.
5. ارفع الشعار/الغلاف/صورة منتج، ثم افتح المتجر للتأكد من ظهورها.

## 5) الاختبارات المطلوبة — وكيف نشغّلها

| الأمر | ماذا يفحص | النتيجة |
|---|---|---|
| `npx tsc --noEmit` | سلامة الأنواع | ✅ بلا أخطاء |
| `npx next build` | بناء الإنتاج (يتضمن فحص أنواع مسارات Next) | ✅ 40 صفحة/مسار |
| `node scripts/verify-rls.mjs` | **RLS حقيقي** على PostgreSQL (PGlite): ينفّذ 0001 + 0003 + 0004 ثم يختبر المالك/الأعضاء/الزائر على كل جدول وكل مسار تخزين، **وينفّذ نفس حمولة حفظ الإعدادات التي يرسلها التطبيق** | ✅ 44/44 |
| `npm run build && node scripts/verify-local-flows.mjs` | **سيناريو كامل عبر HTTP** على الوضع التجريبي: تعديل متجر رشف، رفع شعار/غلاف، إضافة منتج بصورة، تغيير النطاق، متجر «قيد التجهيز»، دخول لوحة المتجر من نطاق المتجر نفسه، حفظ الآيبان/لون التذييل، ومنع صاحب متجر رشف من متجر عود ولوحة المالك | ✅ 55/55 |
| `node scripts/repro-upload.mjs` (يقبل `--no-bucket` / `--wrong-secret-key` / `--no-secret-key` / `--app-dir`) | إعادة إنتاج سبب «فشل الرفع» ومقارنة قبل/بعد | ✅ |

الاختبارات تغيّر بيانات تجريبية محليًا فقط ثم **تُعيدها كما كانت**:

* `verify-local-flows` ينسخ `.data` قبل التشغيل ويعيدها بعده (أو يحذف ما أنشأه).
* `verify-rls` يعمل على قاعدة WASM مؤقتة في الذاكرة — لا يلمس أي قاعدة حقيقية.
* **لا يُحذف أي شيء** من Supabase، ولا تُنشأ بيانات تجريبية على الإنتاج (عدا كائن اختبار
  بحجم 1×1 بكسل يرفعه زر «فحص رفع الصور» ثم يحذفه فورًا).

## 6) ما لم يُنفَّذ داخل بيئة العمل هذه (وكيف تُكمله أنت)

بيئة التنفيذ هنا معزولة عن الإنترنت (لا وصول إلى Supabase ولا إلى Cloudflare ولا بيانات دخول)،
لذلك:

* **لم يُنفَّذ الترحيل على قاعدة الإنتاج** — نفّذه أنت (خطوة 1 أعلاه).
* **لم يُنشر الكود على Cloudflare** — ادمج الفرع ثم أعد النشر (`npm run cf-deploy`)، وبعده
  يعمل `npm run cf-verify` للتأكد من أن ملفات الموقع تُخدَم بـ 200 على `https://waathba.com`.
* **لم يُضغط أي زر في متصفح حقيقي** — لكن كل خطوة تمرّ في مسارها الحقيقي عبر HTTP في اختبار
  `verify-local-flows` (نفس المسارات التي يناديها المتصفح عبر `fetch`).
* بعد الترحيل والنشر: افتح **لوحة المالك → أي متجر → «فحص رفع الصور»** واضغط «تشغيل الفحص»؛
  سيقول لك بالضبط أي طبقة تعمل وأيها لا تعمل — بلا تخمين.
