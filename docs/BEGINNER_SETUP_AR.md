# دليل المبتدئ الكامل — ربط معون بـ Supabase و Cloudflare

> هذا الدليل مكتوب لشخص **لم يستخدم Supabase أو Cloudflare من قبل أبداً**.
> كل خطوة مشروحة بالنقرات. لا تتخطَّ أي خطوة، واتبعها بالترتيب.
> الوقت المتوقع: **45 – 60 دقيقة** (بدون وقت انتظار الـ DNS).

---

## الجزء صفر: افهم ما الذي نفعله ولماذا

قبل أي نقرة، افهم الصورة الكبيرة — هذا سيوفّر عليك ساعات من الحيرة.

موقعك «معون» يتكوّن من جزأين منفصلين تماماً:

| الجزء | ما هو؟ | أين سيعيش؟ |
|---|---|---|
| **الكود** (ملفات Next.js) | الصفحات، التصميم، الأزرار | **Cloudflare** (Workers & Pages عبر OpenNext) |
| **البيانات** (المتاجر، المنتجات، الحسابات، الصور) | الأرقام والنصوص المخزّنة | **Supabase** |

الكود وحده = موقع فارغ. البيانات وحدها = معلومات بلا واجهة.
**الربط** بينهما يتم عن طريق **3 نصوص سرّية** تُسمى «متغيرات البيئة» (Environment Variables) — تأخذها من Supabase وتلصقها في Cloudflare. هذا كل شيء. بقية الدليل تفاصيل.

### ما هو Supabase؟
خدمة تعطيك **قاعدة بيانات PostgreSQL** جاهزة على الإنترنت، مع:
- **Database** — الجداول التي تخزّن المتاجر والمنتجات.
- **Authentication** — نظام تسجيل الدخول (البريد وكلمة المرور).
- **Storage** — مكان رفع الصور.
- **SQL Editor** — نافذة تكتب فيها أوامر لقاعدة البيانات.

### ما هو Cloudflare؟
خدمة تستضيف كود Next.js وتشغّله على شبكتها العالمية. هذا المشروع يجري على
**Cloudflare Workers & Pages** عبر المحوّل الرسمي **OpenNext** (لا نستخدم أداة
`next-on-pages` القديمة المهجورة). تأخذ Cloudflare كودك من GitHub وتبنيه وتنشره،
وكل مرة ترفع تعديلاً على GitHub تنشر النسخة الجديدة تلقائياً.

### كيف يعمل مشروعك الآن (مهم جداً)
في ملف `lib/services/index.ts` يوجد هذا المنطق:

```ts
_services = isSupabaseConfigured() ? getSupabaseServices() : localServices;
```

بالعربي: **إذا** وجد التطبيق متغيرات Supabase → يستخدم Supabase.
**وإلا** → يستخدم قاعدة بيانات SQLite محلية داخل مجلد `.data/`.

النسخة المحلية ممتازة للتجربة على جهازك، لكنها **لا تعمل على Cloudflare إطلاقاً**
(لأن بيئة Workers لا تسمح بنظام الملفات). لذلك إذا نسيت متغيراً واحداً، سيظهر موقعك
**فارغاً** على Cloudflare. هذا أشهر خطأ للمبتدئين، وسنتجنّبه.

## الجزء الأول: Supabase

### الخطوة 1 — إنشاء الحساب

1. افتح المتصفح على: **https://supabase.com**
2. اضغط الزر الأخضر **Start your project** (أعلى اليمين).
3. اختر **Continue with GitHub** — هذا الأفضل، لأنك ستحتاج GitHub لاحقاً مع Cloudflare أصلاً.
4. ستنتقل لصفحة GitHub تطلب الإذن → اضغط **Authorize supabase**.
5. الآن أنت داخل لوحة تحكم Supabase (Dashboard).

> إذا لم يكن لديك حساب GitHub أساساً: افتح https://github.com/signup وأنشئ واحداً أولاً (دقيقتان)، ثم عد هنا.

### الخطوة 2 — إنشاء المشروع

1. اضغط **New project** (زر أخضر في المنتصف أو أعلى اليمين).
2. إذا طلب منك **Organization**: اختر الموجودة أو أنشئ واحدة باسمك.
3. املأ الحقول:

| الحقل | ماذا تكتب | ملاحظة |
|---|---|---|
| **Name** | `maaoun` | اسم داخلي فقط، لا يظهر لأحد |
| **Database Password** | اضغط **Generate a password** | ⚠️ اقرأ التحذير تحت الجدول |

> ⚠️ **كلمة مرور قاعدة البيانات:** بعد توليدها اضغط **Copy** والصقها فوراً في مكان آمن (تطبيق ملاحظات مقفل، أو مدير كلمات مرور مثل Bitwarden). **لن تستطيع رؤيتها مرة أخرى.**

4. اضغط **Create new project**.

### الخطوة 3 — إنشاء الجداول (تشغيل ملف 0001)

الآن قاعدة بياناتك **فارغة تماماً**. سنبني فيها الجداول باستخدام ملف جاهز موجود في مشروعك.

#### 3-أ) احصل على محتوى الملف

الملف اسمه: `supabase/migrations/0001_init.sql` (526 سطراً).

**أسهل طريقة لفتحه ونسخه:**
- إذا كان المشروع على جهازك: افتحه بـ VS Code → اضغط `Ctrl+A` ثم `Ctrl+C`.
- أو من GitHub: افتح المستودع → مجلد `supabase` → `migrations` → `0001_init.sql` → اضغط زر **Copy raw file** (أيقونة مربعين أعلى يمين محتوى الملف).

> ⚠️ **انسخ الملف كاملاً** — من أول حرف إلى آخر حرف. نسخ جزء منه سيسبب أخطاء غامضة.

#### 3-ب) الصقه وشغّله

1. في Supabase، من الشريط الجانبي اضغط **SQL Editor** (أيقونة تشبه ورقة فيها `>_`).
2. اضغط **+ New query** (أعلى اليسار).
3. الصق المحتوى كاملاً في المربع الأبيض الكبير (`Ctrl+V`).
4. اضغط زر **Run** الأخضر أسفل يمين المربع (أو `Ctrl + Enter`).
5. انتظر 5 – 20 ثانية.

#### 3-ج) كيف تعرف أنه نجح؟

✅ **نجح** إذا ظهر أسفل الشاشة: `Success. No rows returned`
❌ **فشل** إذا ظهر مربع أحمر فيه رسالة خطأ.

**أشهر الأخطاء:**

| الرسالة | السبب | الحل |
|---|---|---|
| `syntax error at or near ...` | نسخت الملف ناقصاً | امسح كل شيء، انسخ الملف كاملاً من جديد |
| `relation "stores" already exists` | شغّلت الملف مرتين | لا مشكلة غالباً — انتقل للخطوة التالية |

#### 3-د) تأكّد بعينك

اضغط **Table Editor** في الشريط الجانبي. يجب أن ترى قائمة جداول مثل:
`profiles` · `stores` · `store_members` · `categories` · `products` · `pages` · `settings` … إلخ.

إذا رأيتها — ممتاز، أهم خطوة تمّت. 🎉

**ماذا فعل هذا الملف بالضبط؟**
1. أنشأ كل الجداول.
2. فعّل **RLS** (Row Level Security) — وهي قواعد أمان تمنع عميل «رشف» من رؤية بيانات عميل «عود» حتى لو حاول. هذا هو عمود العزل (Multi-Tenant) في مشروعك.
3. أنشأ صندوق تخزين للصور اسمه **`store-assets`** (تأكد من وجوده: اضغط **Storage** في الجانب).

### الخطوة 4 — إنشاء حسابات الدخول

الجداول جاهزة، لكن لا يوجد أي مستخدم. سننشئ 3.

1. من الشريط الجانبي اضغط **Authentication**.
2. ستفتح على تبويب **Users**. اضغط **Add user** (أعلى اليمين) → اختر **Create new user**.
3. ستظهر نافذة صغيرة. املأها:

**المستخدم الأول — أنت (مالك المنصة):**
- Email: **بريدك الحقيقي** (مثلاً `mohammed@gmail.com`)
- Password: كلمة مرور قوية من عندك (احفظها!)
- ✅ ضع علامة على **Auto Confirm User** — مهم جداً، وإلا لن تستطيع الدخول قبل تأكيد البريد.
- اضغط **Create user**.

**كرّر نفس العملية مرتين:**

| البريد | كلمة المرور | Auto Confirm |
|---|---|---|
| `rshaf@demo.com` | `Rshaf#2026` | ✅ |
| `oud@demo.com` | `Oud#2026` | ✅ |

> هذان حسابان تجريبيان لعرض المتاجر. ستحذفهما قبل الإطلاق الحقيقي (الجزء السادس).

4. الآن يجب أن ترى **3 مستخدمين** في القائمة.

#### 4-ب) اجعل حسابك أنت «مالك المنصة»

الحسابات الثلاثة الآن متساوية. يجب أن ترفع نفسك لرتبة `owner` حتى تصل للوحة المالك.

1. اذهب إلى **SQL Editor** → **+ New query**.
2. الصق هذا، **وغيّر البريد إلى بريدك أنت**:

```sql
update public.profiles
set role = 'owner'
where lower(email) = lower('ضع_بريدك_هنا@gmail.com');
```

3. اضغط **Run**.
4. يجب أن ترى: `Success. No rows returned` — والمهم أنه عدّل صفاً واحداً.

#### 4-ج) تحقّق

استعلام جديد:

```sql
select email, role from public.profiles order by created_at;
```

اضغط **Run**. يجب أن ترى جدولاً بثلاثة صفوف:

```
بريدك@gmail.com    owner
rshaf@demo.com     client
oud@demo.com       client
```

> ❗ **إذا كان الجدول فارغاً تماماً:** معناه أن الـ trigger الذي ينسخ المستخدمين من `auth.users` إلى `public.profiles` لم يعمل — غالباً لأنك أنشأت المستخدمين **قبل** تشغيل `0001_init.sql`. الحل: احذف المستخدمين الثلاثة من Authentication وأعد إنشاءهم الآن.

---

> إن كانت قاعدة الإنتاج **موجودة أصلًا** وفيها متاجر: لا تشغّل `0002`. شغّل مرة واحدة
> `supabase/migrations/0006_rebrand_maaoun.sql` لتحديث الروابط والنصوص العامة فقط.
> اسم مشروع Supabase الداخلي (مثل `waathba`) اختياري تغييره ولا يغيّر رابط `*.supabase.co`.

### الخطوة 5 — تحميل البيانات التجريبية (ملف 0002) — لقاعدة جديدة فقط

هذا يملأ موقعك بمحتوى عربي جاهز حتى لا تراه فارغاً.

1. افتح `supabase/migrations/0002_demo_data.sql` وانسخه **كاملاً** (821 سطراً).
2. **SQL Editor** → **+ New query** → الصق → **Run**.
3. انتظر ~10 ثوانٍ → `Success`.

**ماذا أضاف؟**
- 3 متاجر: **كافيه رشف** (`rshaf`)، **عود وروائح** (`oud`)، **دار رشف للحلويات** (`sweets`).
- 6 أقسام + 7 منتجات بصورها.
- صفحات المتاجر وإعدادات التصميم و SEO.
- 3 باقات أسعار + عرضان + عملان في معرض الأعمال.
- **ربط** `rshaf@demo.com` بمتجر رشف، و `oud@demo.com` بمتجر عود.

> ⚠️ **الترتيب مهم:** لهذا أنشأنا الحسابات في الخطوة 4 **قبل** هذه الخطوة. لو عكست الترتيب لن يحدث الربط.
> الملف **آمن لإعادة التشغيل** — شغّله مرة أخرى بلا قلق إذا احتجت.

#### تحقّق (استعلامان مهمان)

```sql
select subdomain, name, status from public.stores order by created_at;
```

المتوقع:
```
rshaf    كافيه رشف              delivered
oud      عود وروائح             delivered
sweets   دار رشف للحلويات       preparing
```

> `sweets` حالته `preparing` **عمداً** — ليريك كيف يبدو متجر تحت التجهيز في لوحة المالك. لن يظهر للزوار. هذا ليس خطأ.

الاستعلام الثاني (الأهم — يتحقق من الربط):

```sql
select s.subdomain, u.email, m.role
from public.store_members m
join public.stores s on s.id = m.store_id
join auth.users u on u.id = m.user_id
order by s.subdomain;
```

المتوقع **صفّان**:
```
oud      oud@demo.com     owner
rshaf    rshaf@demo.com   owner
```

❗ إذا كانت النتيجة **فارغة**: الحسابات لم تُربط. تأكد أن الحسابين موجودان في Authentication بنفس البريد بالضبط، ثم **أعد تشغيل ملف 0002 كاملاً**.

### الخطوة 6 — نسخ المفاتيح الثلاثة 🔑

هذه أهم خطوة في الدليل كله. هذه المفاتيح هي **الجسر** بين Cloudflare و Supabase.

1. من الشريط الجانبي، اضغط **Settings** (الترس، أسفل القائمة).
2. اضغط **API Keys** (أو **API** في بعض الإصدارات).

افتح ملفاً نصياً على جهازك واكتب فيه ثلاثة أسطر، والصق كل مفتاح أمام اسمه:

| # | الاسم في Supabase | شكله | أين تضعه لاحقاً |
|---|---|---|---|
| 1 | **Project URL** | `https://abcdxyz.supabase.co` | `NEXT_PUBLIC_SUPABASE_URL` |
| 2 | **Publishable key** | يبدأ بـ `sb_publishable_...` | `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` |
| 3 | **Secret key** | يبدأ بـ `sb_secret_...` | `SUPABASE_SECRET_KEY` |

- الـ **Project URL** قد تجده في صفحة **Settings → General** أو في زر **Connect** أعلى الصفحة.
- الـ **Secret key** مخفي خلف زر **Reveal** أو أيقونة عين — اضغطها لتراه، ثم انسخه.

> ⚠️ **انتبه لشكل Project URL:** الصحيح هو `https://abcdxyz.supabase.co` فقط.
> لا تنسخ رابط REST الظاهر في نافذة Connect (ينتهي بـ `/rest/v1`) — لأن التطبيق يضيف `/rest/v1`
> بنفسه، فتصل الاستعلامات مكررة `/rest/v1/rest/v1/...` ويرد Supabase بالخطأ
> `Invalid path specified in request URL`. كذلك لا تضع علامات تنصيص ولا مسافات أو أسطرًا جديدة.

#### 🔒 تحذير أمني — اقرأه مرتين

| المفتاح | الخطورة |
|---|---|
| Project URL | عام تماماً — لا بأس بظهوره |
| Publishable key | عام — مصمّم ليعمل في المتصفح، ومحميّ بقواعد RLS |
| **Secret key** | **خطير جداً** — يتجاوز كل قواعد RLS ويقرأ ويعدّل **كل شيء** |

قواعد الـ Secret key:
- ❌ لا تضعه أبداً في متغير يبدأ اسمه بـ `NEXT_PUBLIC_` (أي متغير بهذه البادئة يُرسل إلى متصفح كل زائر!).
- ❌ لا ترفعه إلى GitHub.
- ❌ لا ترسله في محادثة أو لقطة شاشة أو بريد.
- ✅ إذا انكشف بأي شكل: ارجع لنفس الصفحة واضغط **Rotate / Revoke** فوراً لتوليد بديل.

> ملاحظة: مشروعك يدعم أيضاً الاسمين القديمين `anon` و `service_role` (رأيتها في `lib/supabase/client.ts`). إذا كانت لوحتك تعرض الأسماء القديمة فقط، استخدمها. **لكن لا تخلط بين المجموعتين — اختر واحدة.**

**انتهى Supabase. ✅** الآن ننتقل لـ Cloudflare.

### الخطوة 5-ب — ترحيلات مهمة بعد 0001 (لا تتخطَّها) ⚠️

هذان الملفان يصلحان مشاكل حقيقية ظهرت في الإنتاج: **فشل الرفع** و**فشل حفظ الإعدادات**.
نفّذهما مرة واحدة لكل منهما من **SQL Editor** (الطريقة نفسها: افتح الملف → انسخ → الصق → Run):

| الملف | المشكلة التي يحلّها |
|---|---|
| `supabase/migrations/0003_master_owner_permissions.sql` | يعطي **المالك الرئيسي** كل صلاحيات صاحب المتجر على **كل** المتاجر (بما فيها المسلّمة)، ويضيف سياسات كتابة التخزين لأصحاب المتاجر، **ويُنشئ خزنة `store-assets`** إن كانت ناقصة — وهي من أسباب رسالة «فشل الرفع» |
| `supabase/migrations/0004_store_settings_columns.sql` | يضيف أعمدة `store_settings` الناقصة (لون التذييل + الآيبانات) — بدونها **يفشل أي حفظ للإعدادات أو المظهر** بخطأ `PGRST204` |
| `supabase/migrations/0010_landing_content.sql` | يضيف عمود `landing` إلى `site_settings` — بدونه **لن يُحفظ محتوى الموقع** من صفحة «محتوى الموقع» (الغلاف، الإحصائيات، الخدمات...) |

كلا الملفين **آمن لإعادة التشغيل** ولا يحذف أي بيانات.

**كيف تتأكد بعد التنفيذ؟** افتح لوحة المالك → أي متجر → بطاقة **«فحص رفع الصور»** →
**تشغيل الفحص**: يجب أن تظهر كل الطبقات «سليم».

## الجزء الثاني: Cloudflare

### الخطوة 7 — ارفع كودك إلى GitHub أولاً

Cloudflare تقرأ من GitHub، فتأكد أن آخر نسخة من كودك موجودة على الفرع `main`:

```bash
git status                # تأكد لا يوجد شيء مهم غير محفوظ
git push origin main      # أو ادمج فرع عملك في main أولاً
```

> إذا كنت تعمل على فرع منفصل، ادمجه في `main` عبر Pull Request على GitHub قبل المتابعة — لأن Cloudflare ستنشر من `main`.

### الخطوة 8 — إنشاء حساب Cloudflare ونشر المشروع

1. افتح **https://dash.cloudflare.com** وسجّل الدخول (أو أنشئ حساباً مجانياً).
2. من القائمة: **Workers & Pages** → **Create application** → **Pages** → **Connect to Git**.
3. فوّض Cloudflare للوصول إلى GitHub، ثم ابحث عن مستودع **`WathbaStore`** واضغط **Begin setup**.

> **لا ترى المستودع؟** أعِد ضبط أذونات GitHub لتشمل هذا المستودع ثم عد.

### الخطوة 9 — إعدادات المشروع (⚠️ اقرأ قبل Deploy)

ستظهر صفحة إعداد البناء:

- **Project name**: إن كان المشروع المنشور أصلًا باسم `waathba` **لا تُعد تسميته** إلا إذا قبلت تغيّر رابط `*.pages.dev`. لمشروع جديد يمكن استخدام `maaoun` (يظهر كـ `maaoun.pages.dev`).
- **Production branch**: `main`.
- **Framework preset**: اختر **Next.js**.
- **Build command**: `npm run cf-build`
- **Build output directory**: `.open-next`

**الآن الجزء الحاسم: Environment Variables**

أضف المتغيرات الخمسة التالية للإنتاج والمعاينة:

| # | Key (الاسم — انسخه حرفياً) | Value (القيمة) |
|---|---|---|
| 1 | `NEXT_PUBLIC_SUPABASE_URL` | الـ Project URL من الخطوة 6 |
| 2 | `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | الـ Publishable key |
| 3 | `SUPABASE_SECRET_KEY` | الـ Secret key (اجعله Secret) |
| 4 | `NEXT_PUBLIC_MAIN_DOMAIN` | `maaoun.com` |
| 5 | `DEVELOPER_URL` | `https://maaoun.com` |

#### قواعد ذهبية لتجنّب 90% من المشاكل:

1. **الأسماء حسّاسة لحالة الأحرف.** `next_public_...` خطأ. انسخ الأسماء من الجدول أعلاه بالنسخ واللصق، لا بالكتابة اليدوية.
2. **لا مسافات ولا سطر جديد** في نهاية القيمة. عند اللصق تأكد ألا تكون هناك مسافة مخفية في الطرف.
3. **لا تضع علامات تنصيص** حول القيم. اكتب `https://abc.supabase.co` وليس `"https://abc.supabase.co"`.
4. **اجعل `SUPABASE_SECRET_KEY` سرّياً (Secret)** حتى لا يظهر في الواجهة ولا يُدمج في كود المتصفح.
5. **لا تضف المفاتيح الحديثة والقديمة معاً.** إما `PUBLISHABLE_KEY`+`SECRET_KEY`، أو `ANON_KEY`+`SERVICE_ROLE_KEY`. الخلط يسبب سلوكاً غير متوقع.

> ☁️ **Compatibility flags:** ملف `wrangler.jsonc` في المشروع يضبط `nodejs_compat`
> تلقائياً. إن لم يُطبَّق، أضفه يدوياً من **Settings → Compatibility Flags**.

### الخطوة 11 — الاختبار على رابط pages.dev

افتح رابطك (مثل `https://waathba.pages.dev` أو `https://maaoun.pages.dev`).

> 🔑 **مهم جداً — لماذا نستخدم `?store=` الآن؟**
> على نطاق `.pages.dev` لا يمكن استخدام نطاقات فرعية حقيقية. لذلك `middleware.ts` في مشروعك يحاكيها عبر باراميتر `?store=`. هذا مؤقت، وسيختفي بعد ربط نطاقك الحقيقي في الخطوة 12.

| ما تختبره | الرابط | المتوقع |
|---|---|---|
| الموقع العام | `/` | الصفحة الرئيسية + الباقات + الأعمال |
| لوحة المالك | `/admin` | صفحة تسجيل دخول |
| متجر رشف | `/?store=rshaf` | متجر كافيه رشف بمنتجاته |
| لوحة رشف | `/admin?store=rshaf` | صفحة دخول العميل |
| متجر عود | `/?store=oud` | متجر عود وروائح |

**قائمة اختبار من 6 نقاط — نفّذها كلها:**

1. ☐ الصفحة العامة تعرض الباقات ومعرض الأعمال.
2. ☐ متجرا رشف وعود يعرضان منتجاتهما **مع الصور**.
3. ☐ تدخل إلى `/admin` ببريدك وكلمة مرورك → ترى لوحة المالك وجميع المتاجر الثلاثة.
4. ☐ تسجّل خروج، ثم تدخل بـ `rshaf@demo.com` / `Rshaf#2026` على `/admin?store=rshaf` → ترى **متجر رشف فقط**، ولا ترى بيانات عود. (هذا اختبار الـ RLS — إن نجح فالعزل يعمل.)
5. ☐ تضيف منتجاً تجريبياً من لوحة رشف → يظهر في `/?store=rshaf`.
6. ☐ ترفع صورة منتج → تظهر بعد تحديث الصفحة (هذا يثبت أن Storage والـ bucket `store-assets` يعملان).

إذا نجحت الستة — مبروك، الربط تام والمنصة حيّة. ✅

### الخطوة 12 — ربط نطاقك `maaoun.com` والـ Wildcard

هذه الخطوة تجعل `rshaf.maaoun.com` يعمل مباشرة بلا `?store=`.

> **تحتاج أولاً:** أن يكون النطاق `maaoun.com` مضافاً إلى Cloudflare كمنطقة (Zone)
> نشطة — أي أن Nameservers لدى مسجّل النطاق تشير إلى Cloudflare.

#### ✅ استخدام نطاق غير `maaoun.com`

تم تعديل المشروع ليقرأ الدومين الرئيسي من متغير البيئة تلقائياً. فإذا أردت استخدام نطاق آخر (مثلاً `mystore.sa`):

1. غيّر المتغير في Cloudflare فقط:
   ```
   NEXT_PUBLIC_MAIN_DOMAIN = mystore.sa
   ```
2. أضف النطاق `mystore.sa` كـ Custom Domain للعامل، واضبط `*.mystore.sa` (سجل DNS + Route).
3. **أعد النشر** (إلزامي — متغيرات `NEXT_PUBLIC_` تُحقن وقت البناء).

وستعمل مباشرةً `rshaf.mystore.sa` بلا أي تعديل على الكود.

> اكتب الدومين **وحده**: `mystore.sa`
> وليس `https://mystore.sa` ولا `mystore.sa/` — رغم أن الكود صار ينظّف هذه الصيغ تلقائياً، الأفضل كتابته نظيفاً.

#### 12-أ) أضف النطاق في Cloudflare

1. في لوحة Cloudflare: **Workers & Pages** → العامل الحالي (`waathba` ما لم تُعد تسميته يدويًا) → **Settings → Domains & Routes**.
2. أضف **Custom Domain**:
   - `maaoun.com`
   - `www.maaoun.com`
   Cloudflare ينشئ سجلات DNS والشهادة تلقائياً.

#### 12-ب) إعداد النطاق العرضي `*.maaoun.com`

> ⚠️ Cloudflare **لا تدعم wildcard في Custom Domains**. متاجر العملاء `name.maaoun.com`
> تحتاج أحد الحلين:

**الحل الأسهل (Route + DNS):**

| الإجراء | تطبيقه |
|---|---|
| سجل DNS `CNAME` باسم `*` يشير إلى `maaoun.com` (بروكسي - سحابة برتقالية) | DNS للمنطقة |
| **Route** بنمط `*maaoun.com/*` مع `zone_name: maaoun.com` | Settings → Domains & Routes للعامل |

**الحل الأقوى (عامل Wildcard صغير):** عامل يمرر `x-forwarded-host` (التطبيق يقرأها)
للتعرف على النطاق الفرعي — الكود الجاهز في `docs/DEPLOY_CLOUDFLARE_AR.md` القسم 5.

#### 12-ج) انتظر

إصدار شهادة HTTPS وإعداد السجلات يستغرق **من دقائق إلى ساعة**. حدّث صفحة Domains حتى تتحول إلى **Active**.

#### 12-د) اختبر النهائي

| الرابط | المتوقع |
|---|---|
| `https://maaoun.com` | الموقع العام |
| `https://maaoun.com/admin` | لوحة المالك |
| `https://rshaf.maaoun.com` | متجر كافيه رشف — **بلا `?store=`** |
| `https://rshaf.maaoun.com/admin` | لوحة عميل رشف |
| `https://oud.maaoun.com` | متجر عود وروائح |

## جدول حلّ المشاكل الشامل

### 🔴 الموقع يعمل على جهازي لكنه فارغ على Cloudflare
**السبب الأول عالمياً.** التطبيق لم يجد متغيرات Supabase فرجع للوضع المحلي (SQLite) الذي لا يعمل على Cloudflare.
**الحل:** Workers & Pages → الإعدادات → Variables and Secrets → تأكد من الخمسة، الأسماء مطابقة حرفياً، وبلا مسافات زائدة. ثم **أعد نشر** (إعادة بناء).

### 🔴 عدّلت متغيراً ولم يتغير شيء
المتغيرات تُحقن **وقت البناء**. أي تعديل يحتاج **إعادة نشر/بناء** يدوياً. لا يكفي تحديث الصفحة.

### 🔴 رسالة «وضع Cloudflare Workers يتطلب Supabase»
نسيت متغيرات Supabase (أو أحدها). أضف `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
و`SUPABASE_SECRET_KEY` ثم أعد النشر. الوضع المحلي SQLite خاص بالجهاز فقط.

### 🔴 سجلات Cloudflare تقول `Invalid path specified in request URL`
قيمة `NEXT_PUBLIC_SUPABASE_URL` تحوي مساراً (غالباً `/rest/v1` منسوخاً من نافذة Connect)، فتصل الاستعلامات
إلى `/rest/v1/rest/v1/<table>` ويرفضها PostgREST بالرمز `PGRST125`.
**الحل:** اجعل القيمة `https://abcdxyz.supabase.co` فقط — بلا مسار وبلا شرطة نهائية وبلا تنصيص وبلا أسطر جديدة — ثم **أعد النشر**.
(التطبيق يصحّح القيمة تلقائياً ويطبع تحذيراً في السجلات، لكن الأفضل تصحيح المتغير نفسه.)

### 🔴 تسجيل الدخول صحيح لكنه يعيدني لصفحة الدخول
المستخدم موجود في `auth.users` لكن بلا صف في `public.profiles`.
```sql
select u.email, p.role
from auth.users u
left join public.profiles p on p.id = u.id
order by u.created_at;
```
إذا كان `role` فارغاً (`null`) → المستخدم أُنشئ قبل تشغيل `0001_init.sql`. احذفه وأعد إنشاءه.

### 🔴 حساب العميل يدخل لكن لا يرى متجره
لا يوجد ربط في `store_members`. أعد تشغيل `0002_demo_data.sql` كاملاً (آمن)، ثم تحقق باستعلام العضويات في الخطوة 5.

### 🔴 متجر لا يظهر للزائر
حالته ليست `delivered`:
```sql
select subdomain, status from public.stores;
```
غيّرها من لوحة المالك. (تذكّر: `sweets` مقصود بقاؤه `preparing`.)

### 🔴 الصور لا تظهر
1. تأكد أن bucket `store-assets` موجود في **Storage**.
2. تحقق من سياسات الوصول (Policies) — يجب أن تسمح بالقراءة العامة.
3. صور العرض في `public/seed` تُنشر مع التطبيق ولا علاقة لها بـ Supabase.

### 🔴 الـ Wildcard لا يعمل
1. هل أضفت سجل DNS `CNAME *` (بروكسي) وRoute بنمط `*maaoun.com/*` (أو عامل الـ Wildcard)؟ سجل DNS وحده **لا يكفي** — Cloudflare لا تدعم wildcard في Custom Domains.
2. هل حالة النطاق **Active** مع شهادة HTTPS صادرة؟
3. هل قيمة `NEXT_PUBLIC_MAIN_DOMAIN` تطابق نطاقك بالضبط، وهل أعدت النشر بعد تغييرها؟

### 🔵 كيف أجرّب على جهازي قبل النشر؟
في جذر المشروع ملف **`.env.local`** جاهز للتعبئة (وهو مُتجاهَل من Git، فلن يُرفع أبداً).

- **تجربة محلية سريعة:** اتركه كما هو → يعمل بقاعدة SQLite داخلية ببيانات جاهزة.
- **تجربة Supabase قبل Cloudflare:** املأ المتغيرات الثلاثة ثم أعد تشغيل `npm run dev`.
- **معاينة بيئة Workers محلياً:** `npm run cf-preview` (تعمل على `http://localhost:8787`).

```bash
npm install
npm run build   # ← شغّله دائماً قبل الرفع؛ يكشف الأخطاء قبل أن تفشل على Cloudflare
npm run dev
```

ثم: `http://localhost:3000/?store=rshaf`
